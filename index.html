A technical concept

Give AI agents responsibilities, not just tasks.

A task ends when it is done. A responsibility keeps going: something to watch over, to notice changes in and to keep track of, for days rather than for one prompt. This page describes a small model for building that, and an early experiment that tests it.

Observe deterministically. Judge probabilistically. Remember persistently.

01

Tasks end. Responsibilities don’t.

Most agents are given tasks: a request comes in, work happens, an answer goes out, and the agent forgets. That is the right shape for “fix this bug” or “summarise this thread”. It is the wrong shape for “make sure nothing gets stuck”, which is never finished and never fits in a single run.

A task

Starts
When someone asks.
Ends
When the answer is delivered.
Looks at
Whatever is in the prompt.
Remembers
Nothing, unless told again.
Example
“Find the issues that are stuck.”

A responsibility

Starts
When it is defined, and then holds.
Ends
Only when it is withdrawn.
Looks at
The same signals, on every run.
Remembers
Every case it opened, and why.
Example
“Make sure work doesn’t stay in progress for too long.”

02

Three principles

An agent with a responsibility runs again and again, mostly while nobody is watching. So each part of the work goes to whatever does it most reliably, and each part can be checked on its own.

  1. Observe deterministically.

    What gets looked at is decided by plain, stored queries, not by a model. The same data yields the same observations, and the observations behind a case are kept as evidence that can be inspected later.

  2. Judge probabilistically.

    Deciding whether a situation deserves attention, and saying why, is where a language model helps. It proposes; it does not have the last word. Code checks each proposal: that its subject is eligible, that it is well-formed and that it cites evidence that was actually stored.

  3. Remember persistently.

    Conclusions become cases: durable records that open, collect evidence and resolve when the situation does. Memory lives in stored state, not in a context window, so it carries over from one run to the next.

03

Signals, case instructions, cases

A responsibility is defined by what to observe and what deserves attention. What it produces is cases.

  1. Observe

    Signals

    Stored queries against a system you already use. They run on a schedule, and each run yields observations: which subjects matched, and when.

  2. Judge

    Case instructions

    Plain-language instructions, plus optional hard rules such as a minimum number of observation days. A model reads them together with the evidence and drafts case proposals.

  3. Remember

    Persistent cases

    Proposals that pass a deterministic check become cases. A case names the subject that needs attention, cites its evidence and stays open until the observations change.

04 · Early implementation

Example: “Work in progress for days”

The first experiment is an early Jira Cloud app, built to test this model on one concrete problem: work that sits In Progress and quietly stops moving.

How a run works

  1. Once a day, the app runs the stored JQL query (an hourly trigger retries until that day’s run has completed). Each matching issue is recorded as an observation for that day.
  2. When an issue has matched on enough observation days and has no open case, a language model drafts a case proposal from the instructions and the recorded evidence.
  3. A deterministic reconciler opens the case only if the proposal is about one of the eligible issues and cites evidence the app actually stored. Nothing the model returns sets a status.
  4. When a later run no longer finds the issue, the app resolves the case itself and keeps the days and evidence that led to it.

Where it stands

The app is an early experiment, not a finished product. Its signals are JQL queries, each scoped to one Jira project. It observes, opens and resolves cases; it does not change issues or act on the work, so what happens next is up to people. A Jira admin can describe a new responsibility to an assistant that drafts it, but the draft only takes effect once the admin approves it.

05 · Illustrative

Two more responsibilities, sketched

The same split should carry over to other work that never finishes. These two sketches illustrate the general model; they are not capabilities of the current Jira app, and neither has been built or tested. The first stays in Jira. The second assumes a signal from a support system outside Jira.

Illustrative · Jira

Blocked dependencies

“Make sure blocked work doesn’t wait unnoticed.”

Signal
Issues marked as blocked, and issues with an “is blocked by” link to an issue that is still unresolved. Each day’s matches are recorded, so the evidence shows how long every block has held.
Case instructions
“Say whether the blocker belongs to another team, what else is waiting on it and whether it is worth escalating. Cite the days and links observed. Don’t guess why it is blocked.”
Case
One per blocked issue, with its blockers and the days they were seen. It stays open while the block holds and resolves when a later run no longer finds the block.

Illustrative · Support data

Recurring customer complaints

“Make sure a problem many customers report is seen as one problem.”

Signal
New support tickets that match a stored filter, such as a product area or tag, recorded by day. The query decides which tickets are looked at, not which ones belong together.
Case instructions
“Group tickets that describe the same problem. Say whether a group points to something systemic, such as a defect or a confusing change, or is a set of unrelated complaints. Cite every ticket you group.”
Case
One per pattern, not per ticket. New tickets that fit are added as evidence, so the case shows when the problem began and how it grew. It resolves once no new ticket has fitted for a set number of days.

06

What this is, and what it isn’t

It is

  • A way to structure agent work that never finishes.
  • A split that keeps each part checkable: signals are plain queries that can be re-run, judgments compared with their evidence, cases traced through their history.
  • A model that is being tested on a real, narrow problem before it is generalised.

It isn’t

  • A claim that agents can be left to run on their own. A responsibility narrows what an agent watches and how it reports; it does not hand over the work.
  • A product page. The Jira implementation exists to test the concept.
  • Finished. Acting on cases, signals from more than one system and how responsibilities should be reviewed are open questions.
